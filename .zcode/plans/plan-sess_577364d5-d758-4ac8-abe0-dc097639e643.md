# Fix: Extra white space after footer on /search

## Root-cause understanding (from static analysis)

- The layout (`src/app/[locale]/layout.tsx`) renders **nothing in normal flow after `<Footer/>`** — everything after it is `fixed` or returns `null`. A static page structure therefore cannot produce space below the footer.
- `body` is `flex min-h-dvh flex-col overflow-x-clip` — any node appended to `<body>` at runtime becomes a flex item **after the footer** (dev-mode `<nextjs-portal>` is a documented example), and any element anywhere on the page whose box extends below the footer's bottom edge extends the document's scrollable overflow — which paints as **white, non-inspectable space after the footer**. Both mechanisms match the symptom exactly.
- Since you confirmed the bug also appears in a **production build**, the plan starts with a runtime measurement that will pinpoint the culprit regardless of which mechanism it is (and regardless of dev vs prod).

## Phase A — Reproduce & pinpoint (decisive measurement)

1. Run the app (`next dev`, and later a prod build via `next build && next start` since you reported prod is affected). Open `/ar/search?q=<term with results>` and `/en/search?q=...` at desktop width.
2. Via browser automation, run this audit in the page:
   ```js
   const de = document.documentElement, sy = scrollY;
   const fb = document.querySelector('footer').getBoundingClientRect().bottom + sy;
   ({
     scrollHeight: de.scrollHeight, footerBottom: Math.round(fb),
     gap: Math.round(de.scrollHeight - fb),
     bodyChildren: [...document.body.children].map(el => {
       const r = el.getBoundingClientRect();
       return { tag: el.tagName, id: el.id, cls: String(el.className).slice(0,60),
                top: Math.round(r.top + sy), bottom: Math.round(r.bottom + sy), h: Math.round(r.height) };
     }),
     offenders: [...document.querySelectorAll('body *')].filter(el => {
       const r = el.getBoundingClientRect();
       return r.height > 0 && r.bottom + sy > fb + 1;
     }).slice(0, 15).map(el => {
       const r = el.getBoundingClientRect();
       return { tag: el.tagName, cls: String(el.className).slice(0,80),
                bottom: Math.round(r.bottom + sy), h: Math.round(r.height),
                pos: getComputedStyle(el).position, pe: getComputedStyle(el).pointerEvents };
     })
   })
   ```
   - `gap > 0` confirms real extra scroll height; `bodyChildren` exposes runtime-appended nodes (portals/extensions); `offenders` names the exact element(s) extending past the footer.
3. Cross-checks, in order of likelihood:
   - Toggle `overflow-x-clip` off `<html>`/`<body>` live (`document.documentElement.style.overflowX='visible'`) and re-measure — rules the unusual root overflow config in or out.
   - Repeat in incognito (rules out browser extensions injecting body nodes) and in the prod build.
   - If still unexplained, bisect: disable `reactCompiler` in `next.config.ts`, and toggle the search page's Suspense boundaries.

## Phase B — Fix (surgical, based on what Phase A names)

- **Runtime-appended node to `body`** (portal/extension/announcer): CSS neutralizer per your preference, e.g. `nextjs-portal { display: contents }` in `src/app/globals.css` — dev-tools keep working, zero effect in prod (element doesn't exist there).
- **In-page offender** (some component's box extends past the footer): fix at the source in that component — proper containment (`relative` parent / `overflow-hidden`) or corrected positioning. No blanket `overflow-hidden` hacks on body.
- **Root-overflow quirk** (gap tracks the `overflow-x-clip` classes): adjust `layout.tsx` root classes (e.g. clip on body only) while re-verifying the sticky header and that no horizontal scrollbar returns (the reason the clip exists).
- **Compiler-induced**: disable/bisect `reactCompiler`.

## Phase C — Verify

1. Assert `scrollHeight == footer bottom` (gap = 0) on: `/ar/search` and `/en/search` with results, empty results, filtered state; desktop + mobile (≤991px) widths; dev **and** prod build.
2. Regression-check home and category pages (footer flush there too), sticky header still sticks, ScrollToTopButton/NotificationToast unaffected, no horizontal scrollbar regression.
3. Screenshot the page bottom before/after for visual confirmation, and run the visual judge on the final rendered pages.

Note: the search page's own `pb-16` (`search/page.tsx:72`) is inspectable, normal padding (~64px) — not the bug; it stays unless you want it tightened afterwards.
